# 需求问询 · 方法映射

> 这份文件回答一个问题：**这次问询该用哪种问法？**
> 规范主文件是 `AGENTS.md` 阶段 2（问询规则）与 `references/需求问询.md`（题库与题目结构）。
> 本文件只补一层「需求形态 / 缺口维度 → 方法」的映射，不重复题目数量、选项格式、轮次这些硬规则。
>
> 机器可读版本：`scripts/pick_methods.py`（同一份方法库的 CLI）。
> **两份是同一份数据**：改这里要同步改脚本，反之亦然；脚本 `--selftest` 会检查方法库结构。

## 1. 什么时候用它

阶段 1 预调研之后、阶段 2 开口问之前，先做一次**静默九维扫描**（见 `references/需求问询.md` § 0）。
扫描给出「哪几维缺信息」，本文件的映射给出「缺这个维度该用哪种问法」。

| 输入 | 从哪来 | 例子 |
| --- | --- | --- |
| 需求形态 | 阶段 -1 / 阶段 1 判定的产物类型 | web / cli / data / doc / skill / refactor / automation |
| 缺口维度 | 静默九维扫描缺的那几维 + 阶段 2 补充维 | output、acceptance、constraints、risk… |
| 风险档 | 碰数据 / 不可逆动作 / 隐私 / 线上影响 | data-loss / irreversible / security |

```bash
# 推荐本次问询的方法（人看）
python scripts/pick_methods.py --shape web --gaps output,acceptance --risk data-loss

# 机器可读（交给别的 agent 或写进需求确认.md）
python scripts/pick_methods.py --json --shape refactor --gaps constraints
```

## 2. 方法库（16 条）

「一次问几个」是该方法的**建议题数**，不是独立配额：仍然服从阶段 2 的总量规则
（优先 ≤5 题、硬上限 9 题、最多两轮）。「默认档」决定问不到时的处理：

- **必问**：不问就会写出没法开工的提示词，问不到必须给默认值并标「未确认」。
- **建议**：问不到就按默认值写进第 10 段，不必为它单独加一轮。
- **可选**：用户愿意深聊时展开；否则不占题数。

| id | 方法 | 适用信号（缺口维度） | 一次问几个 | 默认档 | 失败退路 |
| --- | --- | --- | --- | --- | --- |
| M01 | 五问定位 | output / audience / success / examples / 所有需求 | 3 | 必问 | 给 2~3 个具体选项 + 默认值写进第 10 段 |
| M02 | 反向问（非目标） | non-goal / scope | 1 | 必问 | 给 3 条常见反向选项让用户勾 |
| M03 | 参照物锚定 | reference / style / examples | 1 | 建议 | 拿同类产品 / 同类文件的 URL 当参考 |
| M04 | 反例锚定 | reference / non-goal | 1 | 可选 | 给一段反例描述让用户指出哪里不像 |
| M05 | 数值标尺 | performance / scale / acceptance | 1 | 建议 | 给数量级选项（100 / 1 千 / 1 万 / 10 万） |
| M06 | 场景走查 | context / workflow / audience | 2 | 建议 | 按真实一天的操作顺序走一遍，漏步补进第 9 段 |
| M07 | 约束清单核对 | constraints / input | 2 | 必问 | 先报默认技术栈，问「必须用 / 必须不用」 |
| M08 | 数据来源与去向 | input / output / data | 2 | 必问 | 给出输入样本与输出样例位置让用户确认 |
| M09 | 失败兜底 | risk / reliability | 1 | 建议 | 给 3 种兜底策略（跳过 / 报错停 / 回滚）让用户选 |
| M10 | 九维非功能扫描 | performance / security / reliability / compatibility | 3 | 建议 | 按 ISO/IEC 25010 九维给默认档，只问偏离项 |
| M11 | 范围切分 | scope / size | 2 | 建议 | 先做一条端到端最小路径，其余进第 5 段非目标 |
| M12 | 接口 / 字段草案 | data / interop | 2 | 建议 | 先画 3~5 个关键字段让用户改 |
| M13 | 验收口径 | acceptance / success | 2 | 必问 | 给「能跑 / 结果对 / 可交付」三档，再落成 A# 判定 |
| M14 | 权限与安全边界 | security / risk | 2 | 建议 | 按最小权限给默认，让用户确认例外 |
| M15 | 决策记录 | memory / tradeoff | 1 | 可选 | 被放弃的选项与原因写进「假设与开放问题」 |
| M16 | 模型 / 版本核验 | model / recency | 1 | 必问 | 查官方文档；查不到写「未确认」，不编版本号 |

## 3. 需求形态 → 起步清单

形态决定「先问哪几条」；缺口维度再补充。`general` 是所有形态的兜底（M01 / M02 / M07 / M13）。

| 形态 | 起步方法 | 为什么是这几条 |
| --- | --- | --- |
| web | M01 M02 M03 M05 M07 M08 M10 M13 | 界面类最容易缺参照物、规模与浏览器/环境约束 |
| cli | M01 M02 M05 M07 M08 M13 | 命令行工具的核心是输入输出、退出码与性能量级 |
| data | M01 M02 M05 M08 M12 M13 | 数据类必须先钉字段、来源去向与规模 |
| doc | M01 M02 M03 M06 M13 | 文档类缺的是读者、场景与「谁签收」 |
| skill | M01 M02 M03 M07 M13 M16 | 技能定义要能被自动识别，模型 / 版本必须核验 |
| refactor | M01 M02 M07 M09 M10 M11 | 改造类先划边界、保行为、定回滚 |
| automation | M01 M02 M06 M08 M09 M13 | 自动化流程怕漏异常路径与失败兜底 |
| general | M01 M02 M07 M13 | 判不出形态时的最小集合 |

## 5. 风险档 → 强制升级

| 风险档 | 处理 |
| --- | --- |
| data-loss / data（数据丢失） | M09、M14 强制升到「必问」 |
| irreversible（不可逆动作） | M09、M14、M02 强制升到「必问」 |
| security（安全） | M14 强制升到「必问」 |

理由：这三类风险不写进提示词，执行者会在没人拍板的地方替用户做决定。

## 6. 问答记录怎么落盘

每问完一题，把方法名写进 `templates/需求确认.md` 的问询表「方法来源」列，格式：

```text
Q1 | 交付物做成什么形态？ | M01 五问定位 | 单个 HTML 文件 | 第 3 段 / 交付物
```

- 方法来源必须是本文件 §2 的方法名或 `Mxx` 编号；`scripts/check_confirm.py` 会校验这一列（D8）。
- 「落到 prompt.md」列写清这条答案进了第几段 / 哪条 R#，闸门同样校验（D9）。
- 用户答不上来的题，答案列写「未确认：…」，并同步写进第 10 段假设与开放问题。

## 7. 出处与本仓库的本地化

| 来源 | 用在哪 | 标记 |
| --- | --- | --- |
| BMAD-METHOD `bmad-advanced-elicitation`：方法库 + `pick_methods.py` 按信号挑方法 | 「方法 × 信号」这层结构 | `[框架]` |
| spec-kit `/clarify`：一轮 ≤5 个高针对性问题、答案回写 | 题数总量与回写要求（见 `references/需求问询.md`） | `[官方]` |
| ISO/IEC 25010:2023 九维 | M10 的维度表与九维扫描 | `[官方]` |
| 本仓库自研 | 16 条方法的中文表述、默认档三档、风险升级表、与阶段 2/需求确认的接线 | `[设计选择]` |

与 BMAD 的差异：BMAD 的方法库服务于「头脑风暴 / 需求启发」的通用场景，本文件的方法必须能落成
`AGENTS.md` 阶段 2 的一道题、一个选项、一句默认值，并与第 4 道闸门 `check_confirm.py` 的字段对齐；
用不上的方法不进库（宁少不滥）。
