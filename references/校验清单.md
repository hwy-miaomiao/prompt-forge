# 校验清单（阶段 4）

分两类：**机器闸门**（三道）与**人工复核**（必须逐项打勾）。
机器只管结构与段间一致性，人工只管"这个提示词换个人来读会不会做错"。

| 工具 | 查什么 | 什么时候跑 |
| --- | --- | --- |
| ① `scripts/check_prompt.py` | 产出的**长提示词**是否符合 12 段契约 | 阶段 4，不通过不许交付 |
| ② `scripts/check_skill.py` | **本技能自己的定义**（`SKILL.md`）能不能被宿主自动识别、会不会静默失效 | 改过 `SKILL.md`、`AGENTS.md` 或 `references/` 之后必跑 |
| ③ `scripts/check_contract.py` | **段与段之间**对不对得上：`R#` 有没有人干、`未确认` 有没有停下条件、`判定：命令` 里有没有命令 | 阶段 4，与闸门① 一起跑 |
| `scripts/mutate_checks.py` | 把闸门源码改坏 15 处，对应的 `--selftest` 必须变红（证明自测不是空跑） | 改过任何 `scripts/*.py` 之后必跑 |

## 一、机器闸门①：长提示词

```bash
python scripts/check_prompt.py <输出目录>/prompt.md
```

退出码：有 ERROR 时非零。通过条件：**0 ERROR**；WARN 要逐条说明为什么不影响执行。

### ERROR（必须修，修不了就说明清楚）

| 码 | 检查什么 | 怎么修 |
| --- | --- | --- |
| E0 | 全文没有任何 Markdown 标题 | 用 `templates/提示词骨架.md` 的 12 段标题 |
| E1 | 缺少必需段落（12 段契约） | 补上缺的那一段，不要合并段落 |
| E2 | 编号需求 `R#` 少于 3 条 | 拆需求；一条需求一件事 |
| E2b | 同一个 `R#` 编号出现了两次 | 编号必须唯一；新增需求**追加新号**，不要重排 |
| E3 | 编号验收 `A#` 少于 3 条 | 每条需求至少配一条验收 |
| E3b | 同一个 `A#` 编号出现了两次 | 同上 |
| E4 | 某条 `A#` 没引用任何 `R#` | 写成 `A2（对应 R2）`；引用写在**条目的续行**也算（续行里要有「对应 / 覆盖 / 满足 / 实现 / 见」这类声明词，正文顺带提一句不算） |
| E5 | 某条 `A#` 没有 `判定：` | 补 `判定：命令…` / `判定：阈值…` / `判定：人工…` |
| E6 | 某条 `R#` 没有任何 `A#` 覆盖 | 给它配验收，或把它移到第 10 段当假设 |
| E7 | 非目标段为空或只写「无」 | 至少写 1 条不做什么 |
| E8 | 交付物段没有带扩展名的路径 | 写精确路径，如 `out/report.csv` |
| E9 | 需求段/验收段出现模糊词（只要**候选标题**命中该段别名就算，不看最后绑定到哪一条；报的是别的标题时，文案会点名那条标题本身，保留它的编号） | 按 `references/模糊词换算表.md` 换算成数字或判定方式 |
| E10 | 残留占位符（TODO / TBD / 待补充 / 待填 / 待定 / XXX / ???） | 填实或删掉 |
| E11 | `<!-- pf-ignore: W码 理由 -->` 写法不对：没写码、码是 ERROR（豁免只对 WARN 生效）、码不存在于本闸门（在闸门① 里写 `C2` 就会报这条），或者理由不到 4 个字 | 写成 `<!-- pf-ignore: W2 这版先不做量化 -->`；被豁免的 WARN 要照旧不被报出来才算生效，否则先修写法 |

### WARN（可接受，但要解释）

| 码 | 检查什么 | 处理建议 |
| --- | --- | --- |
| W1 | 全文 < 600 字符 | 检查是不是把长提示词写成了短提示词 |
| W2 | 某条 `R#` 没有数字/路径/具体对象（看的是**整条 `R#` 条目**，含它的续行；但不拿别的段落或配对的 `A#` 来判） | 多半不可验证，补量化；量化若写在配对的 `A#` 里，本条可忽略 |
| W3 | 假设段为空 | 一条假设都没有，通常说明替用户拍板了 |
| W4 | 验收条目 > 25 条 | 合并同类项，或分层（必须 / 可选） |
| W5 | 需求条目 ≥ 15 条 | 分层，或拆成两个提示词 |
| W6 | 非目标只写了 1 条 | 补到 2 条以上 |
| W7 | 某条 `R#` 里出现并列句式「，并且 / ，以及 / ，同时」 | 可能是一句多需求，拆成两条（顿号列举、场景里的"同时"不算） |
| W8 | 同一段被**两条以上**标题同时命中，分两种情况：① 一条带编号、一条没编号；② 其中至少还有一条**级别相同**的候选（都带编号或都没编号） | 把该段标题写成规范写法（如 `## 4 需求（R#）`），其余同义标题改掉或删掉，绑定才不会有歧义。两种情况脚本都会把「另一条标题 + 它的行号 + 本次选了哪条 + 为什么选它」一并报出来，照着改就行。**这只是歧义预警**：需求段与验收段的模糊词是按「命中」判的（见 E9），绑定选错也不会把 ERROR 静默降级；其余段落（角色与目标 / 交付物 / 非目标 / 假设）的检查仍按**绑定的那一段**查，绑定顺序 = 段内真有本段条目 → 带编号 → 号数与本段一致 → 文档序号 → 标题级别。**不报的形态**：`## 4. 需求（R#）` 下面再挂一条更深的 `### 4.1 需求补充说明`（级别不同，那是子标题）、「都带编号但级别不同」、「都没编号但级别不同」。`--selftest` 里有专门用例盯着这两个分支 |
| W9 | 非需求段出现模糊词 | 看上下文：背景段的引用可以保留，约束段要换算 |
| E9 / W9 的豁免口径 | 同一份词表：`4 需求（R#）` 段与 `7 验收标准（A#）` 段命中即 **E9**，其余段落命中即 **W9** | 剥掉行首 `>`、`「…」` 引号内容、以及**反引号代码段**后还剩字才算你的锅（反引号是写示例用的口子：把词括起来当例子写，不算你的锅）；所以 `> [用户原话] 「要好看」` 不算，但 `> **R1** 界面要美观` 仍会被抓 —— 加个 `>` 或反引号绕不过闸门 |
| 围栏口径 | 收集"条目"与识别"标题"时**跳过围栏代码块内的行**（``` 与 ~~~ 两种围栏都算）：里面引用的格式示例（`- **R9** …`）不算你的需求，也不算标题 | 少一层保护：围栏里**留着 TODO / 待补充 一样会被 E10 抓到** —— 那是要你填的，不是示例 |
| 豁免注释 | 同一段里写 `<!-- pf-ignore: W码 理由 -->`，该段的这条 WARN 就不报（其余 WARN 照报）：**只对 WARN 生效、必须写理由（≥4 字）、作用域是同段**；写法错报 E11 | 默认做法是改掉它，豁免是例外；确属不必改时再豁免，并在交付回复里逐条说明为什么不影响执行 |
| `--no-ignore` | 闸门① 与闸门③ 都认这个开关：无视豁免，把被压下去的 WARN 全列出来，并提示「另有 N 条按 pf-ignore 豁免」 | 复核"豁免得对不对"时用；CI 不用加 |

## 一之二、机器闸门②：技能定义（能否被自动识别）

```bash
python scripts/check_skill.py SKILL.md          # 检查一个技能定义
python scripts/check_skill.py --selftest        # 自测：仓库里的 SKILL.md 必须 0 ERROR，反例必须命中预期 ERROR 码
```

为什么单独有一道闸门：技能**不靠固定咒语触发**，宿主把 `name` + `description` 交给模型，模型按语义决定用不用。
写错 frontmatter 往往**没有报错**：有的宿主只打一条 warning，模型侧什么诊断都收不到，技能就静默消失了。
机制与出处见 `references/方法论出处.md` 第 4.5 节。

### ERROR（必须修）

| 码 | 检查什么 | 怎么修 |
| --- | --- | --- |
| E1 | 没有 frontmatter、缺 `name` / `description`，或 frontmatter **没闭合**（找不到第二个 `---`） | 补 `---` 包住的 `name:` 与 `description:`；两者都是必填。没闭合的文件会被宿主**整个忽略**（连正文都不读），所以按 ERROR 报 |
| E2 | `name` 不是 kebab-case（大写、下划线、连续/首尾连字符）或超过 64 字符 | 改成 `prompt-forge` 这种形态；别用中文、空格、下划线 |
| E3 | `name` 与**所在目录名**不一致 | 目录包形态就是 `<name>/SKILL.md`：把 `name` 改成目录名，或把目录改名 |
| E4 | `description` 超过 1024 字符 | 删掉背景介绍，只留"何时该用 + 何时不该用 + 做什么" |
| E5 | `description` **前 500 字**里没有"何时该用"的标记（认「当…时 / 如果 / 用户说 / 使用本技能 / 触发」这些说法；「当前」「相当」这类词不算） | 用祈使句开头：「使用本技能：当用户…」「当…时」 |
| E6 | `description` **前 500 字**里没有"何时不该用"的边界 | 补一句「不接：……」，把与相邻能力的边界写清（描述过宽 = 乱触发） |
| E7 | 正文**引用**了同目录的 `AGENTS.md` / `references/` / `scripts/check_prompt.py`，但它不在同目录里 | 薄包装必须整目录一起安装/分发；只拷 `SKILL.md` 会让它指向不存在的规范。自足技能（没引用同目录文件）不查这条。**只有"同目录"才算**：`../AGENTS.md`、绝对路径、盘符路径都是你在指向别处，不算缺件；被引用的**哪些**路径才查哪些。粒度是**文件级**：某条路径在正文任何地方出现过，就算「被引用」（哪怕同段里另有一处写成 `../` 这种不算同目录的写法）；从没出现过的路径才不查 |

### WARN（可接受，但要解释）

| 码 | 检查什么 | 处理建议 |
| --- | --- | --- |
| W1 | `description` 超过 500 字符 | 有的宿主只渲染前 500 字（DSH 的 `catalogDescriptionMaxLength` 默认值），把最强的触发信号放最前面 |
| W2 | 不是祈使句，或混了第三人称自我介绍（「本技能是…」） | 官方指南要求写成给模型的指令；第三人称对路由没有帮助 |
| W3 | 正文**声称了分诊**，却没写全三态（接 `go` / 先问一句 `needs-clarification` / 不接 `kill`） | 自动接住之后要先判断该不该接，再决定进不进流程。标记词按**词边界**匹配（`go` 不会被 `good` 命中），「不接（kill）」也不会被当成写了「接」 |
| W4 | 正文**引用了同目录的 `AGENTS.md`**（= 自称薄包装），却没写"动手前先读完" | 薄包装必须把规范本体的位置与读法写死。只引用 `references/` 或 `scripts/check_prompt.py` 的技能不算薄包装，本条不查 |
| W5 | 正文**给了菜单/选项**，却没写"每项自带默认档、用户可以不选" | 官方口径是 Provide defaults, not menus；本仓库的折中全靠这句话 |

**E7 与 W3/W4/W5 只在正文真的声称了对应机制时才查**（E7 看引用了哪些同目录文件，W3 看有没有写"分诊"，
W4 看有没有引用同目录的 `AGENTS.md`，W5 看有没有菜单）。这是拿真实文件撞出来的教训：早期版本无条件要求这三件事，于是**任何一份与
prompt-forge 无关的自足技能都会被报 ERROR + 3 条 WARN** —— 闸门是在拿本仓库的家规要求别人。
E5/E6 例外：**任何**技能都要求描述里写清"何时该用 / 何时不该用"，这是官方对描述过宽与过窄的判据，不是家规。
判定用的"正文"还会剥掉**围栏代码块**：正文里引用的样例（比如示范用的正确描述）是别人的文字，
不能当成这个技能自己的声明。

**三条实现口径**（改了脚本要一起守住）：
① 只按 `\n` 切行（`split_lines()`），不认 U+2028 之类的"行分隔符" —— 否则报的行号和编辑器对不上；
② frontmatter 值是**合法的 YAML 标量**：支持折行续写、缩进续写、`|`/`>` 块标量、行内 `#` 注释
（引号内的 `#` 不算注释），所以 `description:` 换行写不该被当成"缺 description"；
③ 每个码报的行号指向**真正出问题的那一行**（`name` 行、`description` 行、出问题的正文行），不是文件开头；
④ 正文里的**标记词**按词边界匹配（`go` 不会命中 `good`），「接住」用正则排除了「不接」，中文标记先折叠空白再找（`不 接` 也认）；
   目录名取 `path.resolve()` 的结果（`scripts\..\SKILL.md` 不会误报 E3）；
⑤ 传进来的是目录时报「这是目录，不是文件：…（要给的是 `<技能目录>/SKILL.md`）」，与闸门① 同一口径。

加了新的检查项就补反例：**先用真实文件跑一遍确认期望值**，别照直觉写。

## 一之三、机器闸门③：跨段一致性

```bash
python scripts/check_contract.py <输出目录>/prompt.md
python scripts/check_contract.py --selftest   # 10 个用例 + 1 个 --no-ignore 用例 + 2 个范围说明用例
```

闸门① 管的是「这一段自己写得对不对」，闸门③ 管的是「段与段之间对不对得上」：两者互补，只跑一个不算过。
闸门③ **import 闸门① 的解析器**（段落绑定、条目、`R#`/`A#` 编号都取自同一份实现），
所以闸门① 的绑定与编号口径一改，闸门③ 跟着变，不会各查各的。

### ERROR（必须修）

| 码 | 检查什么 | 怎么修 |
| --- | --- | --- |
| C1 | 引用了**不存在的编号**：第 9 段写「（对应 R7）」，可第 4 段最大只到 R5（`A#` 同理） | 把编号改对，或把那条需求/验收补进对应段落 |
| C3 | 第 10 段列了 `未确认`，第 11 段却是空的 / 只写「无」/ 里面没有可识别的停下条件 | 给每条 `未确认` 配一条「什么情况下停下来问人」 |

### WARN（可接受，但要解释）

| 码 | 检查什么 | 处理建议 |
| --- | --- | --- |
| C2 | 某条 `R#` 没被第 9 段任何一步触及 —— 这条需求没人干 | 在对应步骤后面补 `（对应 R#）`；这版真不做的，就挪进第 5 段非目标写明理由 |
| C4 | 第 10 段的某条 `未确认` 在第 11 段找不到对应（两处没有一个共同的关键词） | 补上那条停下条件，并让两处的用词对齐 |
| C5 | 某条验收写着 `判定：命令`，条目里却没有一条能直接粘贴的命令 | 补命令；给不出命令就把判定改成阈值或人工 |

写提示词时守住两条，闸门③ 就不会红：**第 9 段每个步骤写 `（对应 R#）`**、
**第 10 段每条 `未确认` 在第 11 段有一条停下条件**。

范围说明：闸门③ 只查跨段一致性 —— 段落齐不齐、条目格式对不对归闸门①；
`未确认` 与停下条件的匹配是**关键词重叠**判的（假设段写「导出格式」、第 11 段写「文件怎么存」会被报成 C4），
报出来是提醒你把两处说法对齐，不是要求逐字相同。豁免注释同闸门①：`<!-- pf-ignore: C2 这条这版先不做 -->`
可以压掉 C2/C4/C5 这类 WARN（C1/C3 是 ERROR，豁免不了），写法错报 `E11`；`--no-ignore` 可以看全。

## 二、人工复核（逐项打勾）

### A. 陌生人测试（最重要，一次就够）

- [ ] **把本次对话全部删掉**，只留 `prompt.md`，另一个 AI 能不能读懂？有没有「上面说的」「之前那个」？
- [ ] 每一处**路径**都是可解析的（绝对路径或相对仓库根），没有「合适的位置」「相应目录」。
- [ ] 每一处**版本号**都是具体数字，没有「最新版」「合适的版本」。
- [ ] 每一处**事实**都带来源标记（`[用户原话]` / `[仓库实测]` / `[外部资料 URL]` / `[AI 推断]`）。
- [ ] 每个 `[AI 推断]` 都在第 10 段出现过。

### B. 需求与验收

- [ ] 每条需求都能想象出「做完了长什么样」；想象不出来的重写。
- [ ] 每条验收都引用了需求编号，没有凭空出现的验收。
- [ ] 每条验收的 `判定：` 都能**当场执行或当场看**（不是「测试一下」）。
- [ ] 写着 `判定：命令` 的验收，命令是**真能粘进终端跑**的（闸门③ C5 只查"有没有命令"，命令对不对要人来判）。
- [ ] 带数字的验收都写了**测量方法**（命令、次数、机器）。
- [ ] 验收里没有「通过 / OK / 正常」这类没有口径的词。

### C. 边界与风险

- [ ] 非目标段真的拦得住「顺手扩展」吗？用户看完会不会觉得「我明明说过不要这个」？
- [ ] 有没有**替用户拍板**的地方？每处都进了第 10 段吗？
- [ ] 第 10 段的每条 `未确认`，在第 11 段都能找到一条对应的停下条件吗（闸门③ C3/C4 只按关键词重叠判，
      两处措辞差太远会漏判 —— 人工这一遍要按语义再看一次）？
- [ ] 第 9 段的每个步骤都写了 `（对应 R#）`，并且每条 `R#` 都真的有人干吗（闸门③ C1/C2 查编号与覆盖，
      但"这一步真的在做那条需求"仍然要人来判）？
- [ ] 第 11 段的触发条件是可识别的（不是「遇到问题就问」）？
- [ ] 涉及删除/覆盖/对外发送/花钱的动作，都在第 11 段设了卡点吗？
- [ ] 汇报格式的「三件套」在最后一段写明了吗？

### D. 交付形态

- [ ] `prompt.md` 落在 `<输出目录>/`，没有写进工具目录。
- [ ] `需求确认.md` 记的是**用户原话**与用户的选择，不是你的推断。
- [ ] 回复里贴了长提示词**全文**（不是只说「已写入文件」）。
- [ ] 回复里点了「最可能返工的三处」。
- [ ] 闸门报了几条 WARN，回复里就**逐条列出**几条 WARN 和不影响执行的理由（一条都没有就写「无 WARN」）。

### E. 自动识别与分诊（阶段 -1 / 阶段 2.5）

- [ ] **第一句就把分诊结论说给用户听了**（接 / 先问一句 / 不接），不是心里判断完直接开问。
- [ ] 判「不接」时给了**一句话理由 + 更合适的做法**，并且**没有**启动流程、没有写任何文件。
- [ ] 判「先问一句」时，问的是那**一个决定性前提**，没有顺手问成一整轮，也没把它算进阶段 2 的题目配额。
- [ ] 每条判据都引用了**用户原话里的片段**（而不是"看起来像是个项目"这种印象）。
- [ ] 扩充菜单每一项都带**默认档**，兜底话说清了（「全按默认」也走得通）。
- [ ] 被勾掉或没确认的项没有凭空消失：进了第 5 段非目标或第 10 段假设。
- [ ] 改过 `SKILL.md` 的 `name` / `description` 之后重跑了闸门②（`check_skill.py` 必须 0 ERROR）。

## 三、话术模板（分诊 / 扩充菜单 / 交付）

### 阶段 -1 · 分诊（接住之后的第一句话）

```text
接（go）：「<用户原话片段>」是要交给另一个 AI 去做的活（我理解产物是 <…>），
我按 prompt-forge 的流程来：先做目标体检与预调研，再拿一轮选择题跟你确认。

先问一句（needs-clarification）：「<用户原话片段>」我还不确定是「<可能 A>」还是「<可能 B>」——
这一条决定了后面全部内容，先确认它，剩下的我一次性问完。

不接（kill）：「<用户原话片段>」不用走 prompt-forge：<一句话理由>。
直接这样做更快：<直接执行 / 换个工具 / 直接给答案>。
```

### 阶段 2.5 · 扩充菜单

```text
你说的是这些，我复述一遍：<3~5 条结论>。

这份提示词要不要包含下面这些？（每项都带默认档，不勾就按默认走；嫌麻烦直接说「全按默认」）
- [默认 要] <项目> —— 代价：<加什么、加多少>
- [默认 不要] <项目> —— 要的话代价：<加什么、加多少>
……（6~8 项，最多 12 项）

确认无误请回「准确，开始生成」；要改哪一项直接说。
```

### 阶段 5 · 交付

```text
长提示词已生成：<输出目录>/prompt.md（已过闸门：0 ERROR，N WARN）

WARN 逐条说明（没有就写「无 WARN」）：
- W# <哪一条、出现在哪一段>：不影响执行，理由：<…>

<提示词全文>

最可能返工的三处：
1. <推断项 1>（默认取 …，改一句话要连带改第 X 段与第 Y 段）
2. <推断项 2>
3. <推断项 3>

要改的话直接说「第 X 段改成 …」，我只重做受影响的部分并重跑闸门。
```
