# 方法论出处

本仓库哪些说法**有出处**、哪些只是**本仓库的设计选择**。写文档或做问询时，
不要把「设计选择」讲成「官方推荐」—— 那和"用形容词交差"是同一类错误。

标记：`[官方]` 厂商/标准组织正文 · `[框架]` 权威作者或标准的二手介绍 · `[设计选择]` 本仓库取舍，无出处。

## 1. 问询（阶段 2）

| 结论 | 标记 | 出处 |
| --- | --- | --- |
| 澄清问题**一轮 ≤5 个**、按优先级排序、答案回写文档、必须在动手之前问 | `[官方]` | GitHub spec-kit 的 `/clarify`：<https://github.github.com/spec-kit/reference/agentic-sdd.html> |
| 澄清只问 what / why（用户可见行为与目标），技术选型留到实现阶段 | `[官方]` | 同上（`/specify` 与 `/plan` 的分工） |
| 收尾做一次一致性检查：有没有需求没验收、有没有验收没需求 | `[官方]` | 同上（`/analyze`） |
| **多选题比开放式问题容易**：识别优于回忆 | `[官方]` | NN/g：<https://www.nngroup.com/articles/recognition-and-recall/> |
| 每题 3~4 个选项、首项是推荐项并写理由 | `[设计选择]` | 无出处。唯一依据是上一条「给选项比让人凭空描述容易」 |
| 优先级四档 Must / Should / Could / Won't（本仓库未强制，需要时可加一题） | `[框架]` | MoSCoW（Dai Clegg 提出，DSDM 详述）；来源本身承认"没有客观排序方法"，所以必须让用户自评 |
| 用户故事质量检查 INVEST / SMART（T 原文是 Time-boxed） | `[框架]` | <https://xp123.com/invest-in-good-stories-and-smart-tasks/> |

## 2. 验收标准（第 7 段）

| 结论 | 标记 | 出处 |
| --- | --- | --- |
| `Given` = 前置状态（**不要写用户交互**）、`When` = 单个事件、`Then` = **可观察**结果（不要用"去查数据库"代替可观察行为）、每个例子 3~5 步 | `[官方]` | Cucumber Gherkin：<https://cucumber.io/docs/gherkin/reference/> |
| 非功能需求可照**九维清单**排查（2023 版是九个特性，不是八个） | `[官方]` | ISO/IEC 25010:2023 <https://www.iso.org/standard/78176.html>（ISO 明说可用于 identifying acceptance criteria）；2023 改名对照 <https://iso25000.com/index.php/en/iso-25000-standards/iso-25010> |
| 需求质量可以自动检查（含糊、一句多需求、被动语态、逃逸条款、绝对化词……） | `[框架]` | INCOSE *Guide to Writing Requirements* v4 → 42 条规则 <https://ssaleem74.github.io/incose-requirements-workbench/>；标准本体 ISO/IEC/IEEE 29148:2018 <https://www.iso.org/standard/72089.html> |
| 模糊句 → 可判定句的示范：`within 200 ± 20 ms with MTBF ≥ 5000 hours` | `[框架]` | 同上（INCOSE 工具页 before→after 示范） |
| 每条验收要写判定方法（测试/分析/检查/演示） | `[设计选择]` | 本仓库落成 **命令 / 阈值 / 人工** 三种；INCOSE 的"必须可测量"支持这个方向 |

## 3. 提示词写法（第 3 阶段）

| 结论 | 标记 | 出处 |
| --- | --- | --- |
| 指令放开头、用分隔符区分指令与上下文、减少含糊描述、**说该做什么而不是只说别做什么**、用示例表达期望格式 | `[官方]` | OpenAI：<https://help.openai.com/en/articles/6654000-best-practices-for-prompt-engineering-with-the-openai-api> |
| 明确具体、给动机（解释"为什么"）、给示例（**模型会照抄示例细节，包括坏模式**）、**允许模型说"我不确定"** | `[官方]` | Anthropic：<https://claude.com/resources/articles/best-practices-for-prompt-engineering>；<https://www.anthropic.com/news/prompt-engineering-for-business-performance> |
| 规则放在上下文开头、写成短句 | `[官方]` | Cursor Rules：<https://cursor.com/docs/rules> |
| 12 段骨架本身 | `[设计选择]` | 官方只有"技法建议"，没有"编号段落规范"；这是本仓库的工程取舍 |

## 4. 机器闸门（第 4 阶段）

| 检查项 | 标记 | 依据 |
| --- | --- | --- |
| 模糊词、**逃逸条款**（尽可能、在可行范围内、如需要） | `[框架]` | INCOSE GtWR 的 ambiguity 与 escape clause 规则 |
| 需求必须带 measurement（无数字/路径 → WARN） | `[框架]` | 同上 |
| 有需求没验收、有验收没需求 | `[官方]` | spec-kit `/analyze` 的方向 |
| 占位符残留（TBD / 待补充 / XXX） | `[设计选择]` | 工程惯例；spec-kit 要求把不确定处显式写成 `[NEEDS CLARIFICATION: ...]` |
| 段落缺失、编号重复、交付物无路径、验收无判定 | `[设计选择]` | 本仓库自己的结构约束 |
| **跨段一致性**（闸门③）：需求↔步骤（谁去干）、未确认↔停下条件（谁兜底）、判定↔命令（有没有命令） | `[设计选择]` | 方向与 spec-kit `/analyze` 一致（需求、任务、验收之间要对齐）；具体的 C1~C5、"关键词重叠判对应"、"只查跨段、不重复查段落本体"是本仓库的取舍 |
| WARN 的**豁免注释** `<!-- pf-ignore: W码 理由 -->`（只对 WARN 生效、必须写理由、作用域同段、写法错报 E11） | `[设计选择]` | 静态检查工具的通用惯例（如 lint 工具的 disable 注释要带理由）：允许例外，但不允许悄悄消失 —— 被豁免的条数要报出来，`--no-ignore` 能看全 |
| **变异检验**：把闸门源码改坏，对应的自测必须变红 | `[框架]` | 变异测试（mutation testing）的基本判据 —— 测试的价值在于"它能失败"；本仓库只做 30 处关键判据的轻量版，零依赖实现（`scripts/mutate_checks.py`） |
| 三份自测 + 变异检验 + 三件仓库级检查（资产过闸门 / 反例被拦下 / 全 LF）放进 CI，矩阵跑 Python 3.9 与 3.12 | `[设计选择]` | GitHub Actions 的常规用法；两个版本是为了兑现"零依赖、Python ≥3.9"这个承诺 |

## 4.5 技能定义与自动触发（阶段 -1）／内容扩充菜单（阶段 2.5）

本技能**不靠固定咒语触发**：宿主把 `name` + `description` 交给模型，模型按语义判断这次输入该不该用它。
也就是说，「自动识别」这件事唯一的作用面就是 `SKILL.md` 的 `description` —— 闸门②
（`scripts/check_skill.py`）钉的就是这句话能不能被认出来（何时该用 / 何时不该用）。

| 结论 | 标记 | 出处 |
| --- | --- | --- |
| 模型**靠 name + description 决定要不要触发**这个技能 | `[官方]` | Anthropic：<https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills>「Pay special attention to the `name` and `description` of your skill. Claude will use these when deciding whether to trigger the skill in response to its current task.」；<https://code.claude.com/docs/en/skills>「What the skill does and when to use it. Claude uses this to decide when to apply the skill.」 |
| description 要写成**给模型的指令**（祈使句），而且**宁可写得"推"一点**：把适用场景、包括用户没有直接点名领域的场景都列出来 | `[官方]` | <https://agentskills.io/skill-creation/optimizing-descriptions>「Use imperative phrasing. Frame the description as an instruction to the agent: 'Use this skill when...' rather than 'This skill does...'」「Err on the side of being pushy.」 |
| description 过窄 = 该触发时不触发；过宽 = 不该触发时乱触发；**写宽了就补"不做什么"、把与相邻能力的边界写清** | `[官方]` | 同上：「If should-not-trigger queries are false-triggering, the description may be too broad. Add specificity about what the skill does *not* do, or clarify the boundary between this skill and adjacent capabilities.」 |
| 匹配是**必要非充分**：描述再准，宿主也可能不加载（例如一句话就能干完的单步请求） | `[官方]` | 同上：「A simple, one-step request like 'read this PDF' may not trigger a PDF skill even if the description matches perfectly」 |
| `name` 必须是 kebab-case、≤64 字符、**等于父目录名**；`description` 非空、≤1024 字符 | `[官方]` | agentskills 规范：<https://agentskills.io/specification>（"Must match the parent directory name"） |
| 技能是**渐进加载**的：目录里先只放 name + description（约 100 tokens），正文与资源按需加载 | `[官方]` | 同上（progressive disclosure：Metadata / Instructions / Resources） |
| 宿主渲染进目录的 description 有**长度上限**（本机 DSH 的 `catalogDescriptionMaxLength` 默认 **500**），超出部分不参与路由；`whenToUse` 在 DSH 里**根本不渲染**，对自动触发没用 | `[官方源码]` | DSH 包内规格 `@deepseek-ai/dsh-skill-filesystem` / `@deepseek-ai/dsh-tool-skill`（本仓库实测：frontmatter 写错、名字非 kebab-case、布尔值拼错，技能会被**静默跳过**，模型侧拿不到任何诊断） |
| 三态分诊 `go` / `needs-clarification` / `kill` | `[官方]` | GitHub spec-kit 评估流程：<https://github.github.com/spec-kit/guides/assessment.html>「The result is an evidence-backed `go`, `needs-clarification`, or `kill` decision, not an implementation.」；澄清是"给有真实歧义的东西加的质量闸门"：<https://github.github.com/spec-kit/reference/agentic-sdd.html> |
| 一句话能描述出 diff 就别做计划 —— 单步任务不该启动完整流程 | `[官方]` | Claude Code best practices：<https://code.claude.com/docs/en/best-practices>「Plan mode is useful, but also adds overhead.」「If you could describe the diff in one sentence, skip the plan.」 |
| 大改动**先访谈用户**再动手，而且"别问显而易见的问题，去挖我没考虑到的难点" | `[官方]` | 同上：「For larger features, have Claude interview you first… using the `AskUserQuestion` tool」 |
| 澄清要"在合适的时候"问，并把假设明说出来 | `[官方]` | OpenAI model spec：<https://model-spec.openai.com/2026-08-18.html>「Consider uncertainty, state assumptions, and ask clarifying questions when appropriate」 |
| 阶段 -1 的判据三条（有交付物 / 是不是任务级 / 缺的信息能不能自查）、"误触发成本 > 漏触发成本"的默认倒向、不确定就默认接 | `[设计选择]` | 三态措辞沿用 spec-kit，但**判据与倒向是本仓库自己的取舍** |
| 阶段 2.5「内容扩充菜单」，且**每一项自带默认档** | `[设计选择]` | 与官方「Provide defaults, not menus」（<https://agentskills.io/skill-creation/best-practices>）存在张力：本仓库保留菜单，但把它限制在"**写多厚**"这一层，且每项都有默认档 —— 用户一个都不选，结果与"直接给默认值"一致 |

## 5. 明确**不用**的说法（查不到可靠一手来源）

- Amazon PRFAQ / Working Backwards 的官方段落结构；Definition of Ready 的权威条目清单；5 Whys 的官方正文。
- MoSCoW 的 60/20/20 百分比；spec 模板的逐段标题。
- "24 种 vs 6 种果酱、30% vs 3% 购买率"这两个常被引用的数字（且 *choice overload* 的可复制性本身有争议）。
- "默认选项能显著提高选择率"——这个经典论证已被反驳（器官捐献 opt-out 研究），不要拿它当论据。
- "首项给推荐答案"没有学术或厂商证据：本仓库把它标为**设计选择**，不写成"业界证明"。
- **"description 要写成第三人称"**：查不到一手来源，官方指南要求的是**祈使句**（见 4.5）。别再写这条。
- **"description 匹配就一定触发"**：错，匹配是必要非充分（见 4.5）；所以分诊判据要写在正文里，不能全指望路由。
- **"name 必须等于目录名，不然宿主报错"**：agentskills 规范确实要求一致，但 Claude Code 的 `name` 是**可选**项
  （"Defaults to the directory name"，不匹配也不报错），DSH 则可能把不合规的技能**静默跳过**。
  本仓库按规范从严（`check_skill.py` 的 E3），但不要说成"所有宿主都会报错"。
- **"别问太多问题，用户会烦"**：一手来源里没有这条硬规则，最接近的只有 OpenAI 的"when appropriate"（见 4.5）。
  所以本仓库的题目上限（≤5 题、上限 9 题）标为 `[设计选择]`，不要写成"官方建议"。
