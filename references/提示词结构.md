# 长提示词的 12 段结构（阶段 3）

`prompt.md` 是**给另一个 AI 看的执行指令**，不是给人看的汇报材料。
它要满足一个硬标准：**把本次对话全部删掉，对方 AI 只读这个文件也能开工，且不会猜错。**

## 0. 为什么是这 12 段

| 段 | 回答的问题 | 缺了会怎样 |
| --- | --- | --- |
| 1 角色与目标 | 做成什么样算成功？ | AI 自己定义成功，通常做成"能跑但没用" |
| 2 背景与已知事实 | 已知什么、可信度多少？ | AI 用训练数据里的常识替代你的现实 |
| 3 交付物 | 交什么、交到哪？ | 产物位置随机，用户拿不到 |
| 4 需求 R# | 到底要做什么？ | 漏做、少做、做偏 |
| 5 非目标 | 不要做什么？ | 顺手扩展，动了不该动的东西 |
| 6 技术约束 | 用什么做、不许用什么？ | 引入不该有的依赖，风格不合 |
| 7 验收 A# | 凭什么说做完了？ | "已完成"无法反驳，返工靠吵架 |
| 8 验证方式 | 怎么证明？ | 验收标准没人会算 |
| 9 执行步骤 | 按什么顺序做？ | 顺序错乱，做到一半发现地基不对 |
| 10 假设与开放问题 | 哪些是猜的？ | 猜错的地方静默变成 bug |
| 11 何时停下来问人 | 什么情况下不许自己决定？ | 要么越权，要么鸡毛蒜皮都来问 |
| 12 汇报格式 | 做完怎么说话？ | 交上来一段"已完成"，无法验收 |

## 1. 角色与目标

- 一句话目标 + **成功定义**。写「让 10 分钟内完成首次配置」，不写「提升体验」。
- 需要时补一句角色：「你是负责 X 的工程师」，但**不要用角色扮演替代事实**（"你是世界顶级专家"不产生任何约束）。
- 目标必须能被第 7 段的验收覆盖：目标里的每个名词，验收里都要能找到对应条目。

## 2. 背景与已知事实

每个事实后面标来源，**四选一**：

| 标记 | 含义 | 例子 |
| --- | --- | --- |
| `[用户原话]` | 用户亲口说的，最高优先级 | `[用户原话] 数据只在本机处理` |
| `[仓库实测]` | 你读文件/跑命令得到的 | `[仓库实测] pyproject.toml 里 Python ≥3.11` |
| `[外部资料]` | 带 URL 的公开信息 | `[外部资料 https://…] 该接口限流 5 req/s` |
| `[AI 推断]` | 你的猜测，**默认不可信** | `[AI 推断] 用户可能想要每天自动跑` |

规则：

- `[AI 推断]` 的条目**必须在第 10 段再出现一次**（作为未确认项）。
- 禁止写本次对话里才存在的东西（「上面那个方案」「刚才说的第二种」）。
- 事实与需求分开：背景段只陈述**已经为真的事**，不夹带要求。

## 3. 交付物

写成表或列表，每条含 **精确路径 + 格式 + 数量/大小**：

```text
- `F:\work\download-tidy\tidy.py` —— 单文件 Python 脚本，可 `python tidy.py --dry-run` 直接跑
- `F:\work\download-tidy\README.md` —— 不超过 60 行，含安装、用法、配置项三节
- 终端输出：一次运行打印的移动记录表，含"来源 → 目标"两列
```

禁止：「放到合适的位置」「一个文档」「几个脚本」（`check_prompt.py` 会把它判成 ERROR）。

## 4. 需求（R#）

- 逐条编号 `R1`、`R2`…，**一条需求一件事**。一条里出现「并且」通常该拆。
- 每条都要**可验证**：带数字、文件名、字段名、或明确对象。写「R3 支持导出」不合格，写「R3 导出一份 `report.csv`，列固定为 date,amount,category」合格。
- 排序 = 优先级顺序（AI 中途被打断时，前面的已经做完）。
- 拿不准的需求**不要写进来**：进第 10 段。

写法对照：

| 不合格 | 合格 |
| --- | --- |
| R2 整理得整洁一点 | R2 按扩展名分到 `图片/文档/压缩包/其他` 四个子目录，同名文件追加 `-1`、`-2` |
| R4 做好错误处理 | R4 单个文件移动失败时跳过并记入 `errors.log`，其余文件继续处理 |
| R5 性能要好 | R5 1000 个文件（约 5 GB）在本机 SSD 上 ≤ 30 秒完成 |

## 5. 非目标

- **必须写实**：写「无」是 ERROR，只写 1 条会 WARN（建议 2 条以上）。
- 三类最该写：① 用户可能期待但这次不做的；② 容易被顺手扩展的；③ 会破坏现有行为的。
- 例子：`不做云同步`、`不改动现有数据库表结构`、`不引入需要联网的依赖`、`不做 GUI`。

- **同一件事优先写正面要求，而不是只写禁令**（OpenAI 口径）：只列"别做什么"时，执行者知道自己被禁止了什么，
  却不知道该做什么 —— 能写成正面要求的就别只写禁止。
- 反过来说：非目标段的作用是**拦住顺手扩展**，所以宁可多写一条。

## 6. 技术约束

按这张清单逐个交代（不适用的写「不限」）：

- 语言与版本（`Python 3.11` / `Node 20` / `Go 1.22`）
- 允许/禁止的依赖（默认「只用标准库」，要加依赖必须写明包名与理由）
- 目录与文件位置、命名规范
- 代码风格（现有仓库的规范文件路径；没有就写「跟随同目录现有文件风格」）
- 环境（OS、是否可联网、是否需要管理员权限）
- 明确禁止项（`禁止引入 <某框架>`、`禁止修改 <某文件>`）

**版本必须写具体数字**，不写「最新版」。

**模型名 / 模型版本 / API 默认值要核官方文档**：技术约束里一旦出现具体模型名、模型版本号或 API 的默认参数
（例如多模态输入上限、默认超时、默认上下文长度），必须先查该厂商官方文档确认，并把核验结论写出来；
查不到就写进第 10 段并标 `未确认`，**不许凭记忆编**。闸门① 的 W10 会在「出现模型名但全篇没有任何核验/未确认说明」时提醒。

## 7. 验收标准（A#）

每条 `A#` 由三部分组成，缺一不可：

```text
A2（对应 R2）：跑 `python tidy.py --dry-run` 后，`图片/` 下的文件数与输入一致；
   重复运行不会产生移动记录。判定：命令 `python tidy.py --dry-run` 输出 0 条移动记录，人工核对文件数。
```

1. **编号 + 引用需求**：`A2（对应 R2）` —— 一条 A# 可以引用多条 R#，但每条 R# 至少被引用一次。
2. **可观察的结果**，不是动作（写「输出包含 X」而不是「实现了 X」）。
3. **`判定：`** 三选一：
   - `判定：命令 <命令> —— 期望 <输出/退出码>`
   - `判定：阈值 <指标> <数字>（测量方法：<怎么量>）`
   - `判定：人工 <谁> 看 <什么>，<什么算通过>`

强验收的标准形状是 **Given / When / Then**：

```text
A3（对应 R2）：给定 `图片/` 已有 `a.jpg`，当再次放入同名 `a.jpg` 并运行脚本，
   则新文件名为 `a-1.jpg` 且两个文件都存在。判定：命令 `python tidy.py && ls 图片/` 期望出现 a.jpg 与 a-1.jpg。
```

写成 Given / When / Then 时守住三条（Cucumber 口径）：`Given` 只写**前置状态**，不要把用户点击写进去；
`When` 只写**一个**事件；`Then` 写**可观察**的结果 —— 「查了数据库发现值对」不算可观察，
要写成界面/接口/文件上能看见什么。一个验收 3~5 步就够，步骤堆多了反而失焦。

## 8. 验证方式

- 一段**可以直接复制粘贴执行**的命令清单（含工作目录），顺序与执行步骤一致。
- 每条命令后写**期望输出**（关键行、退出码）。
- 写清**失败怎么办**：哪条不过就回到哪个步骤，而不是「调试一下」。
- 如果验证需要用户配合（登录、插设备、给数据），在这一段点名。

## 9. 执行步骤

- 阶段化：`步骤 1 建目录 → 步骤 2 实现核心移动 → 步骤 3 加 --dry-run → 步骤 4 写 README → 步骤 5 自测`。
- **每步都要有产物**（文件、可运行的命令、一段输出），没有产物的步骤是假步骤。
- **每步都要写它对应哪条需求**：`2. 实现分类移动 → 产物 tidy.py（对应 R1、R2）`。
  每条 `R#` 至少被一个步骤提到 —— 漏掉的那条没人干（闸门③ 的 C2 会点出来）；
  这版真不做的需求，就挪进第 5 段非目标写明理由，别让它在步骤段里烂尾。
- 标出**可中断点**：做完哪几步就能先给用户看。
- 标出**顺序依赖**：哪些步骤不能调换。
- 每步做完自己先跑第 8 段对应的命令，**不要攒到最后一起验**。

## 10. 假设与开放问题

两种条目，格式固定：

```text
- 未确认：日志写到哪（默认取 `tidy.log` 放在脚本同目录；不对就说，改一行）
- 开放问题：是否需要处理 `.part` 之类的半成品下载文件（本次按"不动"处理）
```

- 所有 `[AI 推断]` 都要在这里出现。
- 每条假设必须给**默认取值**和**改起来多贵**（一行 / 一个文件 / 重做）。
- **每条 `未确认` 都要在第 11 段有一条对应的停下条件**，而且两处**用同一批关键词**
  （都写「日志路径」、都写「导出格式」）—— 否则执行的人只能自己拍板。
  闸门③ 的 C3/C4 查这条：第 11 段空着报 C3，两处找不到共同关键词报 C4。
- 这一段的长度是健康指标：**一条假设都没有，通常说明你替用户拍板了。**
- 确实缺、又必须先写进文档的信息，用显式标记 `[NEEDS CLARIFICATION: <缺什么>]` 标出来：
  标记要能对上这里的一条 `未确认`（闸门① E13 查格式、E14 查它和本段是否自洽；
  闸门③ C6 查标记在第 10 段有没有对应的「未确认」）。标记末尾写缺什么，一句话说清，不要只写一个空壳。

## 11. 何时必须停下来问人

写**可识别的触发条件**，不是「有问题就问」。典型：

- 需要删除或覆盖已有数据
- 需要对外发请求/发消息/提交代码/花钱
- 需要访问密钥、账号、生产环境
- 需求内部出现冲突（两条 R# 不能同时满足）
- 验收标准明确不通过，且修它需要改需求本身

每条写清：`触发条件 → 停下来做什么（问什么、给什么选项）`。

## 12. 汇报格式

规定对方 AI 完成后的回话结构，**默认三件套**：

```text
1. 改了什么：按文件/产物列清单（路径 + 一句话）
2. 怎么验的：逐条 A# 贴命令与结果（通过/不通过）
3. 还剩什么：未确认项、没做到的、需要用户拍板的
```

加一句硬要求：**任何 A# 不通过，不许写「已完成」**，要写「A3 未通过，原因是 X，建议 Y」。

**汇报前先自证**：写死一句「汇报前先按第 8 段的命令自己跑一遍，把真实输出贴出来；没有自证不许说已完成」。
这是 verification-before-completion 的本地化 —— 让执行者先证明再汇报，而不是先宣称再补证据。
闸门① 的 E12 查这一段有没有这句意思（自证/先自己验/先跑一遍再汇报等同义写法都认）。

- 明确写一句**允许执行者说"我不确定"**（Anthropic 口径）：例如
  「数据不足以下结论时，直接说『这里我没有把握』，不要用推测填空」—— 否则它会为了显得能干而编。
- 三件套的顺序固定：**改了什么 → 怎么验的（贴命令与结果）→ 还剩什么**。
  没有"怎么验的"就不算汇报，只算通知。

## 13. 长度与密度

- 没有字数下限，但**有信息密度下限**：任何一句话删掉之后执行结果不变，就删掉。
- 经验区间：脚本/小工具 400~900 字；Web 应用 800~2000 字；重构类 600~1500 字。
- `check_prompt.py` 的 W1（<600 字）只是提醒，不是要求凑字。
- 长提示词**不是越长越好**：把「背景故事」写成三屏，只会稀释真正的约束。
