# 需求问询（阶段 2 唯一强制卡点）

这一阶段只做三件事：**问对问题**、**让用户挑而不是让用户写**、**把答案钉成可判定的事实**。
用户答完并说「准确，开始生成」之后，才允许进阶段 3。

## 1. 三条硬规则

| 规则 | 数值 | 违反的后果 |
| --- | --- | --- |
| 题目数量 | **优先 ≤5 题，上限 9 题，一轮问完** | spec-kit 的 `/clarify` 就定在"一轮 ≤5 个针对性问题"；超过 9 题，用户开始敷衍，答案质量塌方 |
| 选项数量 | 每题 **3~4 个**，首项带理由 | 选项超过 5 个 → 选择瘫痪；只有 1 个 → 变成通知 |
| 轮次 | **最多 2 轮** | 第 3 轮说明你没做阶段 1 预调研 |

- 超过**优先值（5 题）**时的处置：把次要项**改成默认值**并写进假设段（标 `未确认`），把题目让给影响最大的项；
  硬上限仍是 9 题 —— 若已经问到 9 题还压不住，就继续把次要项挪进假设段，不能靠第 3 轮补问。
- 至少 **一半的题必须是选择题**；开放题最多 2 个。
- 每题必须有「都可以 / 你决定」兜底项 —— 用户有权不决定，代价是它变成一条显式的假设。

## 2. 每题的固定结构

```text
Q3. 交付形态（影响：交付物段落 + 验收段落）
- [推荐] 单个 Python 脚本 + README —— 理由：你只要求「双击能跑」，脚本最容易验证，也最少维护
- 带子命令的 CLI 工具（--dry-run / --undo）
- 带界面的小应用（要额外写 UI，工期 ×2）
- 都可以 / 你决定
```

四个要点：

1. **题号 + 题目 +「影响哪一段」**：让用户知道这道题值不值得认真想。
2. **推荐项永远放第一，并写出理由**：用户照抄首项也能得到合理结果。
3. **选项要写代价**，不只写好处（「工期 ×2」「需要额外账号」）。
4. **兜底项**：`都可以 / 你决定` → 走默认值 + 假设段。

## 3. 必问题库（按需求形态裁剪，顺序不要乱）

前 4 题几乎任何需求都要问；后面按形态取。

| # | 题目 | 为什么必问 | 常见默认值 |
| --- | --- | --- | --- |
| 1 | **交付物是什么形态**？（脚本 / CLI / 库 / Web 应用 / 文档 / Skill / 数据） | 决定交付物段落与整个技术约束 | 能跑的最小形态 |
| 2 | **谁来用、在什么场景用**？（只有你自己 / 团队 / 陌生人） | 决定易用性、文档量、错误处理强度 | 只有用户自己 |
| 3 | **第一版做到什么程度算够**？（一次性用完就扔 / 能长期跑 / 要给别人用） | 决定验收强度与测试要求 | 自己用、能重复跑 |
| 4 | **有没有必须参照的东西**？（竞品、截图、老代码、旧提示词） | 这是「给参考答案」的最好入口 | 无 |
| 5 | 技术栈与运行环境（语言、版本、OS、有没有既定依赖） | 写进技术约束段 | 用户工作区已有栈 / 最通用的栈 |
| 6 | 数据从哪来、到哪去（输入源、输出格式、权限边界） | 决定需求与验证方式 | 无外部系统 |
| 7 | 性能/规模量级（数据量、并发、时长上限） | 验收标准里的数字来源 | 小规模（写明数量级） |
| 8 | 绝对不做什么（非目标、禁区、不能碰的东西） | 非目标段的唯一来源 | 不引入付费服务、不改现有行为 |
| 9 | 出问题谁来兜底、什么情况下必须停下来问你 | 「何时必须停下来问人」段的来源 | 涉及删数据/发外部请求就停下来问 |

> 判定标准：任何一题的答案都能**直接变成 `prompt.md` 里的一句话**；变不成的题就是没问对，重写。

## 4. 按需求形态增补的题

| 形态 | 增补问题 |
| --- | --- |
| Web / 应用 | 部署到哪（本机 / 内网 / 公网）？要不要登录与权限？浏览器兼容范围？离线可用吗？ |
| CLI / 脚本 | 输入是文件还是交互？失败了要不要回滚？跑一次多久算可接受？要不要幂等（重复跑不重复干活）？ |
| 数据处理 / 报表 | 数据量级与字段口径？口径谁定的？异常数据怎么处理（丢弃/落盘/告警）？多久跑一次？ |
| 文档 / 内容 | 给谁看、看完要做什么决定？篇幅与结构有硬要求吗？有没有必须引用的来源？ |
| Agent Skill / 提示词 | 目标 AI 是谁？触发词怎么写？装了之后落在哪个目录？验收时拿什么例子试？ |
| 重构 / 修 bug | 现状哪一段最难受？允许改多少（只改一个文件 / 允许换依赖）？怎么证明没改坏行为（回归基线）？ |
| 自动化流程 | 触发条件？失败重试几次？通知发到哪？密钥从哪来？ |

## 4.5 非功能需求的九维清单（ISO/IEC 25010:2023）

不用凭空想"还要问什么"：把下面九维过一遍，**只把与本次需求真正相关的维度**变成问题（通常 1~3 维）。
ISO 官方明确说这个模型可用于 identifying acceptance criteria，所以每一维问出来的答案都能直接变成 `R#` 与 `A#`。

| 维度（2023 版名称） | 该问的一句话 | 落到哪一段 |
| --- | --- | --- |
| 功能适合性 Functional Suitability | 哪些功能必须有、哪些可以后补？ | R# + A# |
| 性能效率 Performance Efficiency | 数据量/并发/耗时上限各是多少？ | R# + A#（阈值） |
| 兼容性 Compatibility | 必须在哪些系统/浏览器/版本上跑？要不要与既有系统交换数据？ | 技术约束 |
| 交互能力 Interaction Capability | 谁用、要学多久、出错时看到什么？（2023 版把 Usability 改成了这个名字） | R# + A#（人工） |
| 可靠性 Reliability | 连续跑多久不能出错？失败后怎么恢复？ | R# + A# |
| 安全性 Security | 谁能访问？密钥从哪来？日志里能不能出现敏感信息？ | 技术约束 + 非目标 |
| 可维护性 Maintainability | 以后谁改？改一处最多动几个文件？要不要留测试？ | 技术约束 |
| 灵活性 Flexibility | 换机器/换数据规模/加一个同类渠道要改多少？（原 Portability） | 假设段 |
| 安全无害性 Safety | 会不会损坏数据、误删、伤人？失败时默认往哪边倒？ | 非目标 + 第 11 段 |

注意：2023 版是**九个**特性（新增 Safety，Usability → Interaction Capability，Portability → Flexibility），
照八维的旧清单问会漏掉 Safety 与 Flexibility。

## 5. 给用户「参考」的三种方式（用户要的就是这个）

1. **选项菜单**：从 `references/参考样例库.md` 里挑现成的选项组（产物形态、技术栈、质量档位、验收强度、视觉风格）。
2. **参照物**：让用户给截图、链接、竞品名、老项目路径 —— 一句「参照 X 的信息密度」比十句形容词有用。
3. **反例**：「不要做成 XXX 那样」——用户很难描述想要什么，但非常擅长指出讨厌什么。

组合用法：**先给菜单，用户挑不出时再要参照物，最后用反例收口。**

## 6. 用户答「你决定 / 都行 / 随便」时

不要追问，按下面三步走：

1. 取该题的**默认值**（上表最后一列，或 `参考样例库.md` 的推荐项）。
2. 写进 `prompt.md` 的「假设与开放问题」段，格式：`未确认：<决定内容>（默认取 X，理由 Y；不对就说，我改）`。
3. 交付时在「最可能返工的三处」里点名这一条。

**禁止**：把默认值写进需求段当成用户确认过的事实。

## 7. 问询之后：内容扩充菜单（阶段 2.5）

问询问的是「**做什么**」，菜单给的是「**写多厚**」。这条界线很硬，混了就会变成「让用户配置一切」：

| | 问询（阶段 2） | 扩充菜单（阶段 2.5） |
| --- | --- | --- |
| 回答什么 | 做什么、给谁用、什么算做完 | 这份提示词要不要包含 X（错误处理 / 性能预算 / 部署回滚…） |
| 缺了会怎样 | 没法开工 | 照样能开工 |
| 谁决定 | 只有用户能回答，必须问 | 每项都有默认档，用户不选就按默认走 |
| 数量 | 优先 ≤5 题（上限 9 题） | 按形态取 6~8 项（上限 12 项） |

### 7.1 菜单长什么样

```text
这份提示词要不要包含下面这些？不勾的就按默认走；嫌麻烦直接说「全按默认」。
- [默认 要] 错误处理与失败路径 —— 代价：+2 条需求、+1 条验收
- [默认 要] 边界与空数据 —— 代价：+1 条需求
- [默认 要] 幂等（重复跑不重复干活） —— 代价：+1 条需求、+1 条验收
- [默认 不要] 性能预算（要写数字与测量方法） —— 代价：+1 条阈值验收
- [默认 不要] 部署与回滚步骤 —— 代价：+1 段步骤、密钥来源要问清
- [默认 不要] 单元测试与覆盖率门槛 —— 代价：工期 +30%~50%
```

（完整选项组见 `references/参考样例库.md` 的 K 组，这里只示范格式。）三件事必须做到：

1. **每项自带默认档，并写清代价**（加几条需求、工期加多少）。官方口径是 "Provide defaults, not menus"
   （给人默认值，而不是让人做选择题）；本仓库的折中就是：菜单只出现在「写多厚」这一层，
   且**用户一个都不选 = 直接给默认值**。取舍出处见 `references/方法论出处.md` 第 4.5 节。
2. **一次给完**（6~8 项一组），不要一项一项追问 —— 追问就变成了配置向导。
3. 用户回「你决定 / 都可以 / 全按默认 / 没回」→ 照默认档走，**不再追问**。

### 7.2 勾选结果怎么落

- 记进 `需求确认.md` 第 3.5 节（每项一行：项目 / 默认档 / 用户选择 / 落到 `prompt.md` 哪一段）。
- 勾「要」的项：写进 `prompt.md` 对应段落（`R#`、`A#`、技术约束、验证方式）。
- 勾「不要」的项：**不许凭空消失** —— 属于该形态常见项的（例如"不写错误处理"）写进第 5 段非目标；
  只是这次不需要的写进第 10 段假设，标 `未确认` + 默认取值。
- 菜单结束才是确认点：把「问询结论 + 菜单勾选 + 假设清单」一起复述一遍。

## 8. 问询结束的收尾（写 `需求确认.md`）

用 `templates/需求确认.md` 的格式，至少包含：

- 分诊结论（阶段 -1：接 / 先问一句 / 不接 + 一句理由）
- 用户原话（需求原文，一字不改）
- 每题的**用户选择**（不是你的推断）
- 阶段 2.5 的菜单勾选（含默认档，以及每项落到 `prompt.md` 哪一段）
- 已知事实清单（标来源：用户原话 / 仓库实测 / 外部资料）
- 显式的假设清单（每条带默认值与影响范围）
- 一句确认话术：「以上若有偏差请指出；确认无误请回 **准确，开始生成**」

## 9. 反面例子

| 别这么问 | 为什么不行 | 改成 |
| --- | --- | --- |
| 「你想要什么样的功能？」 | 让用户写需求，等于没问 | 给 3 个功能范围档位让他挑 |
| 「性能要求高吗？」 | 形容词换形容词 | 「并发多少 / 单次跑多久可接受？」给 3 个量级 |
| 「技术栈用什么都行吗？」 | 用户通常不知道 | 给菜单：「[推荐] Python 3.11 + 标准库（零依赖）／Node 20／你已有栈：<路径>」 |
| 「要不要测试？」 | 没有代价信息 | 「[推荐] 只写 1 个冒烟脚本（10 分钟）／pytest 覆盖核心分支（1 小时）／先不写」 |
| 一次问 15 题 | 用户直接弃答 | 优先留 5 题（上限 9 题），其余变假设并标注 |
| 把扩充菜单问成必答题（一项一项追问） | 用户被当成配置项；官方口径也不支持 | 一次给完 6~8 项，每项带默认档，不选就照默认走 |
| 菜单里塞「谁来用 / 什么算做完」 | 混淆了「做什么」与「写多厚」，那道题属于阶段 2 | 只有用户能回答的进问询（≤5 题），菜单只放「要不要包含 X」 |
