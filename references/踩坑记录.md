# 踩坑记录（开工前通读一遍）

每条都是「症状 → 原因 → 正确做法」的形态。这些都来自真实的返工，不是理论风险。

## 1. 形容词原样进了需求段

- **症状**：提示词里写着「界面美观」「性能好」，AI 交上来一版，用户说「不是这个感觉」，然后开始无限改。
- **原因**：形容词没有判定口径，AI 只能猜，猜中的概率极低。
- **正确做法**：按 `references/模糊词换算表.md` 换算；换不出来的去要参照物（截图/链接/竞品）。
  一句话：**你写不出来的数字，AI 也猜不出来。**

## 2. 一次问了 15 个问题

- **症状**：用户答了前 4 题就回「差不多都行」，或者直接不答了。
- **原因**：用户不是需求分析师，问得越多，单题答案质量越低。
- **正确做法**：**优先 ≤5 题、上限 9 题、一轮问完**；把次要项改成默认值写进假设段。宁可 6 道好题 + 3 条标注假设。

## 3. 替用户拍板，而且没标注

- **症状**：交付时用户说「我没说要存数据库啊」，前面所有工作变成返工。
- **原因**：把推断写进了需求段，看起来像用户确认过的事实。
- **正确做法**：所有推断集中进第 10 段，标 `未确认` + 默认值 + 改动代价。
  **假设段的长度是健康指标**：一条都没有，通常说明你在拍板。

## 4. 提示词里写了「参照上面的截图」「按刚才说的方案」

- **症状**：用户开了一个新会话，新 AI 说「我没看到截图」，然后自己编了一套。
- **原因**：把本次对话的上下文当成了共享上下文。
- **正确做法**：提示词是给**陌生人**看的。截图要给路径或 URL；方案要重述；
  用户原话要引用原文。写完做一次「陌生人测试」（见 `references/校验清单.md` 人工复核 A）。

## 5. 验收写「功能正常」「能打开就算过」

- **症状**：AI 回「已完成」，用户打开一看全是坑；或者反过来，AI 做的质量远高于必要。
- **原因**：没有判定口径的验收等于没有验收，好坏全凭谁声音大。
- **正确做法**：每条 A# 必须带 `判定：`，且形如「给定 X，做 Y，出现 Z」。
  「能打开就算过」这种地板验收要写明是**有意为之**（一次性脚本），否则它会一路拉低质量。

## 6. 判定方式只写「跑一下测试」

- **症状**：交付时没人知道要跑哪条命令，最后靠手动点两下确认。
- **原因**：验证方式没落到可复制的命令上。
- **正确做法**：第 8 段给**可以直接粘贴**的命令（含工作目录），并写期望输出与退出码。

## 7. 交付物写「放在合适的位置」

- **症状**：产物散落在用户桌面、仓库根目录、临时目录里，用户找不到。
- **原因**：路径没写死。
- **正确做法**：交付物写成表：**精确路径 + 格式 + 规模**。`check_prompt.py` 的 E8 会拦下这一类。

## 8. 需求一口气写了 30 条

- **症状**：AI 挑最好做的做，难的悄悄跳过。
- **原因**：没有分层，也没有优先级顺序。
- **正确做法**：需求排序 = 优先级顺序；超过 15 条就分层（必须 / 可选），或者拆成两个提示词。
  `R#` 只追加、不重排，方便用户对号入座。

## 9. 只在需求段写了「不许做的事」的暗示

- **症状**：AI 顺手删了旧文件、改了公共接口、加了一个必须联网的依赖。
- **原因**：非目标段缺失或写成「无」。
- **正确做法**：非目标至少 2 条，写三类：用户可能期待但不做的、容易被顺手扩展的、会破坏现有行为的。

## 10. 数字写了，但没写怎么量

- **症状**：「≤ 30 秒」被用最有利的方式量（预热过、空数据集、跑一次取最好值），验收形同虚设。
- **原因**：缺测量方法。
- **正确做法**：阈值一律附测量方法：命令、数据量、跑几次、取哪次、什么机器。

## 11. 版本写「最新版」

- **症状**：半年后提示词失效，或者在一个锁了旧版本的仓库里跑不起来。
- **正确做法**：写具体版本号；依赖写包名与版本，其余默认「只用标准库」。

## 12. 把闸门当质量保证

- **症状**：`check_prompt.py` 0 ERROR，用户却依然说「这不是我要的」。
- **原因**：机器只检查**结构**（段落齐不齐、编号对不对、有没有判定），检查不了**需求本身对不对**。
- **正确做法**：闸门只负责拦住低级错误；「需求对不对」只能靠阶段 2 的问询与人工复核。
  两者缺一不可。

## 13. 把示例当模板套

- **症状**：不管是脚本、网站还是文档，产出的提示词长得一模一样，连技术栈都一样。
- **原因**：直接抄了 `examples/` 而没重新推导。
- **正确做法**：抄**结构**，不抄**结论**。技术约束、验收数字、非目标必须从这个需求重新推。

## 14. 让用户「详细描述一下需求」

- **症状**：用户回了一段更模糊的话，还带着情绪。
- **原因**：把分析工作推回给了用户。
- **正确做法**：**让用户挑，不让用户写**。给 3~4 个带代价的选项，首项是带理由的推荐项
  （菜单见 `references/参考样例库.md`）。

## 15. 用户说「你决定」时追问了三轮

- **症状**：用户烦躁，最后随便选了一个，反而更差。
- **原因**：把「不决定」当成了「没说清」。
- **正确做法**：「你决定」是**授权**，不是缺口。给默认值 + 写进假设段 + 在交付时点名为「最可能返工处」。

## 16. 假设段的默认值没写改动代价

- **症状**：用户以为改一个词就行，实际要重做三节。
- **正确做法**：每条假设写清「改起来：一行 / 一个文件 / 重做第 4 段」。
  这一栏是用户决定「现在纠不纠正」的依据。

## 17. 靠字面咒语触发

- **症状**：用户只是想聊聊技术方案，技能被强行拉起来问了一轮；或者用户换了个说法（「我想做个东西」），
  技能该动的时候一动不动。
- **原因**：`description` 写成了句式枚举（「用户说『帮我做个 X』『我有个想法』时调用」）——
  枚举永远盖不全，而且把"该不该接"这件事交给了字符串匹配。
- **正确做法**：description 写成**语义判据 + 边界**（什么时候该用 / 什么时候不该用），
  正文里写清分诊三态与判据三条；机制与出处见 `references/方法论出处.md` 第 4.5 节。

## 18. description 写得过宽，不该触发时乱触发

- **症状**：随口问一句「这个接口怎么调」也被当成新需求，然后开始问交付物路径。
- **原因**：只写了"做什么"，没写"不做什么"。官方口径：描述过宽 = 在不该触发的时候触发。
- **正确做法**：补一句「不接：……」，把与相邻能力的边界写清（单步任务、纯问答检索翻译闲聊、
  用户明确说别问）。`check_skill.py` 的 E6 会拦下没有边界的 description。

## 19. frontmatter 写错，技能静默消失

- **症状**：技能"装上了"，但模型好像从来没调用过，也没有任何报错。
- **原因**：宿主校验 frontmatter 时**不通过就跳过整个技能，且往往只打一条 warning**，模型侧收不到诊断；
  常见的错法：`name` 不是 kebab-case、布尔值写成 `True`/`yes`（大小写敏感的那几种拼法）、
  `description` 缺失。
- **正确做法**：改完 `SKILL.md` 就跑 `python scripts/check_skill.py SKILL.md`；报 ERROR 就是会静默失效的那种错。

## 20. name 与目录名不一致

- **症状**：文档里写 `/pf-forge`，但安装出来的目录叫 `prompt-forge`，
  换个宿主按目录名调用就找不到。
- **原因**：为了本地路径适配顺手改了 `name`，而目录包形态的规范是 `<name>/SKILL.md`。
- **正确做法**：`name` 必须等于父目录名（`check_skill.py` 的 E3）；要改名字就连目录一起改，
  并在交付说明里显式写出"调用名变了"。

## 21. 以为写了 `whenToUse` 就更容易触发

- **症状**：认真写了 `whenToUse`，触发行为没有任何变化。
- **原因**：宿主渲染进模型目录的只有 `name` + **截断后的 description**（DSH 默认上限 500 字符），
  `whenToUse` 不参与路由；描述超出的部分同样不参与。
- **正确做法**：把最强的触发信号（何时该用 + 何时不该用）压进 description 的**前 500 字**。

## 22. 分诊判完不说出口

- **症状**：用户莫名其妙被问了 5 个问题，不知道为什么要问、还要答几轮。
- **原因**：心里判断完直接开问，把"我为什么觉得这是个项目"藏起来了。
- **正确做法**：接住之后第一句话就给出判断与理由（引用用户原话片段），再进阶段 0。

## 23. 把扩充菜单做成了"让用户配置一切"

- **症状**：用户看着 12 项清单说「你看着办吧」，然后开始敷衍。
- **原因**：菜单里混进了只有用户能回答的问题（那类问题属于阶段 2），或者每项都要用户先表态才有默认值。
- **正确做法**：菜单只管"这份提示词**写多厚**"，**每一项自带默认档** + 一句兜底
  「不勾就按默认走；嫌麻烦直接说『全按默认』」。用户一个都不选，结果必须与"直接给默认值"一致。

## 24. 围栏里的"格式示例"被当成了真条目

- **症状**：需求段里贴了一段 ```text 的写法示例，闸门① 报
  `ERROR: E6 需求 R9 没有任何验收条目覆盖它`——那条 R9 只是示例。反过来更糟：整份文档的
  R#/A# 都写在围栏示例里，正文一条真条目都没有，闸门却是 `0 ERROR 通过`。
- **原因**：判定条目和判定标题是两套口径 —— 标题会跳过围栏，条目收集却把围栏里的行也算进去了。
- **正确做法**：围栏是**引用别人的文字**，收集条目时必须一起跳过（闸门① 的 `collect_items` 现在与
  `split_sections` 同口径）。注意例外：**占位符 E10 仍然扫围栏**——围栏里留着 `TODO` 一样会红。

## 25. 同义标题抢走绑定，段内模糊词从 ERROR 静默降级成 WARN

- **症状**：需求段里写着「界面要好看」，闸门只报 `WARN: W9`，`结果：0 ERROR —— 通过`。
- **原因**：E9 当初只查"绑定到的那一段"，而绑定可能落在一条**空的**带编号同义标题上
  （`# 4 需求（R#）` 压在真需求段 `## 需求（R#）` 上方就赢），于是真需求段的模糊词没人按 ERROR 查。
- **正确做法**：ERROR 级检查按**标题别名命中**判，不按绑定判：只要有一段标题命中"需求/验收"的别名，
  那个段落的模糊词就必须是 E9。排序键只决定 W8/W9 文案里点名哪一段，不承担正确性。

## 26. 把"只在…时触发"当成了"何时不该用"

- **症状**：description 写着「只在需求模糊时触发」，闸门② 的 E6（没有边界）放行。
- **原因**：`只在` 是**触发条件**的措辞，不是排除式边界；它跟「不接 / 不该用 / 不用来」不是一回事。
- **正确做法**：E6 只认排除式说法。要过闸门就得真写一句「不接：……」（单步任务、纯问答检索翻译、
  用户说别问了）。顺带：`不 接`（中间带空格）、全角空格、大小写不同的英文写法都算同一条边界 ——
  匹配前会先把空白折掉。

## 27. frontmatter 没闭合，闸门报"通过"

- **症状**：`SKILL.md` 开头写了 `---` 和 `name`/`description`，却忘了收尾的 `---`；
  宿主把整个技能忽略掉（连正文都不读），闸门② 却报 `0 ERROR`。
- **原因**：解析器把"找不到收尾"当成了"文件没有 frontmatter"的另一种形态，于是既不报 E1，
  又把正文当成空字符串继续检查 —— 两头都不报。
- **正确做法**：frontmatter 状态分三种：`ok` / `missing`（报 E1）/ `unclosed`（也报 E1，
  文案直接说"会被宿主整个忽略"），后两种立即返回，不再对空正文继续检查。

## 28. 合法 YAML 写法被闸门当成语法错误

- **症状**：`description:` 换行缩进续写、`name: prompt-forge  # 备注`、
  `description: >` 块标量，全都被闸门② 报成"缺 description"或"name 不合规"。
- **原因**：手写的 `key: value` 解析只认单行单值、不剥行内注释，而宿主用的是**真 YAML 解析器**。
- **正确做法**：值按 YAML 标量的常见形态解析（折行续写、缩进续写、`|`/`>` 块标量、行内 `#` 注释）；
  别把"我没想到的合法写法"报成错。另外只按 `\n` 切行，U+2028 不是换行符 —— 否则报的行号和编辑器对不上。

## 29. 自测用例是空跑的

- **症状**：把闸门脚本的某处故意改坏，`--selftest` 仍然全绿。
- **原因**：用例的期望值与实际行为在"改不改都成立"的区间里。真实例子：为了盯住"围栏里的条目不算数"，
  用例只往围栏里放了 1 条 `R#` —— 但"编号不足 3 条"这条 ERROR 剥不剥围栏都会报，用例等于没写。
- **正确做法**：写完用例，**把被测代码改坏一次看它会不会红**（变异测试）；红了才说明它真在看。
  期望值必须先用真实文件跑一遍确认，不能照直觉写。

## 30. 模板标题里塞进了段落别名，害用户多一条 WARN

- **症状**：仓库自带 `templates/提示词骨架.md` 被闸门① 报 `WARN: W8`，说第 1 段有两条同义标题
  （`# 任务：<一句话目标，动词开头>` 与 `## 1. 角色与目标`）。
- **原因**：段落别名（第 1 段 = `目标` / `角色`）是**子串**匹配，模板标题里的"目标"两个字正好命中；
  绑定本身没选错（带编号优先），但模板是给人抄的，用户抄完还得替你解释这条 WARN。
- **正确做法**：给人抄的模板自己必须先干净 —— 标题别用段落别名里的词（改成"一句话说清要做什么"），
  并且把 `templates/提示词骨架.md` 单列成 `--selftest` 的一个用例（要求 **0 ERROR 0 WARN**），
  以后谁再往标题里塞"目标"，自测立刻变红。

## 31. 报错文案与行号对不上：命中的是另一条标题，文案却说"需求段"

- **症状**：文档里除 `## 4 需求（R#）` 外还有一条 `## 需求变更由谁说了算`，后者正文里写了"好看"，
  闸门报 `ERROR: E9 「需求（R#）」段出现模糊词「好看」(第 40 行)` —— 用户跑到第 40 行一看是别的标题，
  以为闸门指错了地方。
- **原因**：E9 的判据已经从"绑定"改成"命中"（见第 25 条），但文案还固定用段名，
  命中第二条标题时就成了误指。
- **正确做法**：被查的那一段不是最终绑定的那一段时，文案点名**它自己的标题**
  （`「需求变更由谁说了算」段出现模糊词…`），同时 W8 会提示"两条标题在打架，改掉一条" ——
  改完标题这条 E9 自然消失。

## 32. 正常换行排版被报"没引用需求"（E4 假红 + 连带假 E6）

- **症状**：一条 `A#` 写得长，把 `（对应 R1、R7）` 换行写到了下一行续行 —— 于是闸门报
  `ERROR: E4 验收 A1 没有引用任何需求编号`，紧接着 `ERROR: E6 需求 R1 / R7 没有任何验收条目覆盖它`。
  一份内容本来合规的提示词，卡在"0 ERROR 才允许交付"上。
- **原因**：同一个条目表里两套口径 —— 判定 `判定：` 用的是**整条条目块**，判定"引用了哪个 `R#`"却只在
  标记那一行里找。Markdown 列表的续行属于同一条目，正常排版就会踩中。
- **正确做法**：引用也按整条条目块找，但要认**声明词**（`对应 / 覆盖 / 满足 / 实现 / 见`）——
  正文里顺带提一句 `R2` 不算覆盖，这个口径不能丢。

## 33. 标记词用子串匹配：`good` 命中 `go`、"不接（kill）"命中"接（"

- **症状**：一份正文只写了"做分诊：不接（kill）这类闲聊"的技能，W3（三态没写全）**不报**；
  另一个夹具里"这个技能 good 用"也被算成写了 `go`。三态判据整个空转。
- **原因**：标记匹配是"去掉空白后的子串包含" —— `go` 命中 `good`；而"接住"的标记当时写成裸 `接（`，
  `不接（kill）` 里正好有这半截。**第二个成因更隐蔽**：光给 `go` 加词边界仍然是假绿。
- **正确做法**：短 ASCII 标记按**词边界**匹配（`go` 不命中 `good`）；"接住"用正则排除"不接"
  （`(?<!不)接[（(]`）；中文标记先折叠空白再找（`不 接` 也认）。每种写法都补一条反例用例。

## 34. 「当前」「相当」让 E5 空转

- **症状**：`description` 里没有任何"何时该用"，却过了 E5 —— 只因句子里有「当前只支持 Windows」。
- **原因**："何时该用"的标记表里有裸字「当」，子串匹配把「当前 / 当时 / 相当」全算进去了。
- **正确做法**：收成有语境的模式（`当…时` / `当用户`），落单的「当」不认；
  同理「触发」「适用」要排除「不触发」「不适用于」—— 否则 E5 会在最需要它的时候空转。

## 35. 目录名用词法取，路径里带 `..` 就误报 E3

- **症状**：`python scripts/check_skill.py "scripts/..\SKILL.md"` 报
  `E3 name「prompt-forge」与所在目录名「..」不一致`，同一文件裸名调用却是 0 ERROR。
- **原因**：目录名取的是 `path.parent.name`（纯字符串处理），`..` 没有被解析。
- **正确做法**：取 `path.resolve().parent.name`；顺手把"传进来是个目录"的诊断与闸门① 统一成
  「这是目录，不是文件：…（要给的是 `<技能目录>/SKILL.md`）」。

## 36. 新闸门第一次跑，红的是仓库自己的正例

- **症状**：闸门③（跨段一致性）写完自测全绿，第一次跑仓库自己的资产就连红三处：
  `examples/例1-下载文件夹整理.prompt.md` 报 `C2`（第 4 段的 `R5` 没有任何步骤触及）、
  `examples/例2-班级报名网站.prompt.md` 报 `C4`（第 10 段的 `未确认` 在第 11 段找不到对应）、
  `templates/提示词骨架.md` 同时报 `C2` + `C4`。
- **原因**：新检查项上线时，正例与模板**还没写上它要看的标记**：第 9 段的步骤缺 `（对应 R#）`、
  第 10 段的 `未确认` 与第 11 段的停下条件用了两套措辞。闸门没错，是契约多了一条，正例没跟上。
- **正确做法**：把正例与骨架当成新契约的**基准件**——先补标记（`（对应 R5）`、两边对齐的关键词），
  再让闸门跑绿；并把"自家资产必须过闸门"写进 CI。教训是：正例不是装饰，它是契约的活文档，
  改了契约却不改正例，等于宣布新规矩没人遵守。

## 37. 跨段检查自己重写一套解析器，两套口径开始打架

- **症状（差点踩）**：写闸门③ 时最容易的做法是"再解析一遍段落和条目"。
- **原因**：同一份提示词会有两套段落绑定、两套条目识别、两套编号提取；闸门① 改了绑定口径，
  闸门③ 不会跟着变，于是同一份文件在一个闸门里 `R5` 存在、在另一个闸门里不存在。
- **正确做法**：`check_contract.py` **import 闸门①**，段落切分、条目收集、`R#`/`A#` 提取全部复用；
  闸门③ 只写"段与段之间"的新逻辑。零依赖不是零复用。

## 38. 豁免注释差点变成"消警告的橡皮"

- **症状（差点踩）**：`<!-- pf-ignore: W2 -->` 一写，W2 就不报了 —— 连"为什么可以不管"都不用说；
  更糟的是写成 `pf-ignore: E9` 也能把 ERROR 压下去。
- **原因**：把豁免实现成"过滤掉这些码"，而不是"声明我知道这条 WARN 在说什么"。
- **正确做法**：豁免**只对 WARN 生效**（拿 ERROR 码去豁免报 `E11`）、**必须写理由**（< 4 字报 `E11`）、
  **作用域限同段**、写法错（码不存在 / 没写码）一律 `E11`；并且被豁免的条数要在结果里说出来
  （「另有 N 条 WARN 按 `pf-ignore` 注释豁免」），`--no-ignore` 能把它们全列出来 ——
  看不见的 WARN 没法在评审时复查。这条对应红线 13。

## 39. 变异脚本的锚点凭记忆写，出现 0 次

- **症状**：`scripts/mutate_checks.py` 里"把排序键改坏"那条变异，跑出来是
  `变异点在源码里出现 0 次` —— 我按"修好之后应该长什么样"的印象写了 `old`，把方向写反了。
- **原因**：做"把源码改坏"的工具时，锚点是**真实源码的一行**，不是你以为的那一行；
  源码一改（哪怕只是换个键序），锚点就悄悄失效。
- **正确做法**：`old` 从真实源码里**复制**（本次锚点是
  `            return (not c[5], not c[3], not c[4], c[0], c[2])`，`check_prompt.py:470`），
  并且把"锚点在源码里出现次数必须恰好 1"设计成硬失败 —— 锚点过期要报错，不能静默跳过；
  改完源码就重跑一次 `mutate_checks.py`（对应红线 14）。

## 40. 变异检验把仓库复制成临时目录，目录名一换闸门先红

- **症状**：变异检验第一版把仓库复制到随机名临时目录，闸门② 的用例先红了 ——
  报的是 `E3 name「prompt-forge」与所在目录名「tmpXXXX」不一致`，真正要验的变异被淹没。
- **原因**：闸门② 的 E3 是"`name` 必须与所在目录名一致"，它关心的是目录名，而复制出来的临时目录不叫 `prompt-forge`。
- **正确做法**：镜像目录名固定成 `prompt-forge`（脚本里的 `MIRROR_DIR_NAME`）；同理，
  先在**未变异**的镜像上跑一遍基线，基线不绿就整体失败 —— 否则"变异被抓到"的结论毫无意义。

## 41. `Path.write_text()` 默认换行，把 LF 仓库写成 CRLF

- **症状**：用 Python 脚本改仓库文件，`git diff` 里整文件都变了（每行末尾多个 `\r`），
  在 `* text=auto eol=lf` 的仓库里尤其难受。
- **原因**：`Path.write_text()` 的 `newline=None` 会做平台换行转换，Windows 上写出 CRLF。
- **正确做法**：写仓库文本一律显式 `open(..., newline="\n")`（闸门② 里就是 `write_text_lf`）或走
  `read_bytes`/`write_bytes`；**不要**用 `write_text(..., newline="\n")` —— 那个参数是 3.10+，见 #42。
  再在 CI 里加一道兜底：`git ls-files --eol | grep -E '^i/(crlf|mixed)'` 命中就失败 —— 看的是**索引**里的真实行尾。
  不要用 `git grep $'\r'`：启用 `eol=lf` 后工作区换行已被归一，那条命令永远不命中（第 4 轮审计 P18）。

## 42. `Path.write_text(newline=...)` 是 Python 3.10+ 的参数，本机全绿说明不了 3.9

- **症状**：CI 的 `3.9` 那一格红在「三个闸门的自测」，`3.12` 那一格全绿；本机（只有 3.12）怎么跑都是全绿。
  拿到 3.9 解释器后，真正的报错是：
  ```
  File ".../scripts/check_skill.py", line 607, in selftest
      path.write_text(text, encoding="utf-8", newline="\n")
  TypeError: write_text() got an unexpected keyword argument 'newline'
  ```
- **原因**：`Path.write_text()` / `Path.read_text()` 的 `newline` 参数是 **Python 3.10** 才加的；
  为了守住「全部 LF」（#41）而用的写法，正好踩破了本仓库「零依赖、Python ≥3.9」的承诺。
  静态排查还会漏掉它：`ast.parse(feature_version=(3, 9))` 过、3.10+ API 关键词扫描也没有命中 ——
  **这是「函数签名」层面的版本差异，不是语法或 API 清单能查出来的**。
- **正确做法**：
  1. 需要「写出来一定是 LF」时，用显式 `open`：`with path.open("w", encoding="utf-8", newline="\n") as handle:`
     （闸门② 里封装成 `write_text_lf(path, text)`），3.9 与 3.12 都能跑；
  2. **Windows 上**本机没装 3.9 也能自查：把官方 embeddable 包解压即用（无需安装、脚本零依赖）——
     `https://www.python.org/ftp/python/3.9.13/python-3.9.13-embed-amd64.zip`（8.6 MB）解到 `%TEMP%\py39embed\py39\`，
     然后 `& "$env:TEMP\py39embed\py39\python.exe" -X utf8 -B scripts/check_skill.py --selftest`
     分别跑三份 `--selftest`、`scripts/mutate_checks.py` 与资产实跑（`mutate_checks.py` 用
     `sys.executable` 起子进程，所以在哪个解释器下跑就验哪个版本）；
     macOS / Linux 没有这个 Windows 嵌入包，得装真正的 3.9（见 `README.md` 的「本机只有 3.12 时」一段）；
  3. 最省事的还是让 CI 矩阵兜底（3.9 + 3.12），但**推送前**用上面这条自查一遍，能省一次红。

## 43. 文档承诺的豁免口径，代码只实现了一半（同一句话加不加反引号结论相反）

- **症状**：`校验清单` C1 行写着「A2 出图这类纸张规格豁免」，可提示词里写「打印纸张大小 A4」会被报
  `C1 引用了不存在的 A4`，同一句把 `A4` 括成反引号又不报了 —— 用户照着文档修，怎么改都像在撞运气。
  C5 同类：文档说「反引号里的命令名 + 参数就算命令」，可 `` `echo ok` ``、`` `grep -c 1 x.csv` `` 照样报
  「没有能粘贴的命令」；E10 文档没写「行内代码里的占位符不报」，W5 文档写「写了用户可以不选就不报」，
  但词表只认 4 个固定短语。
- **原因**：豁免分支是分几次补的 —— 规格词在前的写法只加给了行内代码分支，普通文字分支还停在「只看后缀」；
  命令词表只收了构建/运行时命令，忘了通用 shell 命令；文档行数是后来补的，措辞没跟着代码走。
  **文档与代码各改各的**，中间没有人拿同一句话同时喂给两边做对照。
- **正确做法**：同一类豁免必须**一个判据两个入口都走**（`_paper_spec_near` 同时给普通文字与行内代码，
  而不是一个用前后缀、一个只用后缀）；扩词表要先写反例（普通英文词 `find the` / `sort 一下` 仍算没给命令），
  再补变异（把词表退回旧版必须变红）。文档里每条「承诺」都要有一条 selftest 用例与一条变异盯着。
  第 8 轮审计的 5 条修复就是这么收口的：R8-01 纸张语境两入口同口径、R8-02 通用 shell 命令、
  R8-03 W6 按条数、R8-04 W5 可选性词表、R8-05/06 文档措辞与豁免口径。

## 44. 按「行数」数条目、报错不带行号：一条续行就能骗过 W6，一条豁免注释就能压掉全文

- **症状**：非目标段只写 1 条，但后面跟了一行续行说明（或写成「表头 + 分隔行 + 1 行数据」的表格），
  W6「非目标只写了 1 条」不报了；反过来，`<!-- pf-ignore: W6 理由 -->` 写在**任何一段**都能把它压掉。
- **原因**：旧判据是行数比较（`§5 非空行 < 2`），续行/表头把行数凑够了；而 `Finding` 没带行号时，
  豁免逻辑按「文件级」处理 —— 这本来是给 W1 全文长度用的口子。
- **正确做法**：数**条目**不数行（列表符号开头的行 + 表格的数据行，表头与分隔行不算），
  并且给每条 WARN 都带行号，让「同段豁免」真正只对同段生效；补同段生效、跨段不生效两条用例，
  再补「退回按行数」与「退化成文件级」两处变异。**凡是能被人一眼看穿的口子，都要先想它会不会被当成消警告的捷径。**
